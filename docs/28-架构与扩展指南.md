# 28 · 架构与扩展指南

> 2026-11-10 重构定稿。目的只有一个：**加一个功能、删一个功能，改动落在一处**。

## 0. 这次重构动了什么、没动什么

重构前有三个「所有功能都必须挤过去」的咽喉，加/删一个功能要在里面多处手改：

| 咽喉 | 病 | 重构后 |
|---|---|---|
| `config.json` 的 schema | 同一个字段在 `config-migrate.ts`（读盘）、`config-merge.ts` 的 `toPublicConfig`（出主进程）和 `mergeConfigPayload`（保存）**手写三遍**，靠注释提醒「三处必须同步」 | §1：字段注册表，一个字段一处定义；结构性变更走版本迁移步骤表 |
| `src/main/app.ts`（1874 行） | 全部 IPC handler、全部 store、云/AI/运行器接线都在一个文件 | §2：`app.ts` 只剩组合根；每个功能一个 `features/<名>.ts` |
| IPC 契约 | 通道在 `ipc-channels.ts`、preload、主进程三处各写一遍，漏一处只能运行时发现 | §3：静态契约闸门（单测） |

**没动的（有意）**：渲染层（`views/` + `stores/` + `components/domain/` 已经按功能分；路由是一张懒加载表）、`src/shared/` 的纯函数、`src/main/` 下已成目录的子系统（`cloud/` `runner/` `env/` `ai/` `study/` `store/`）、`preload/index.ts`（白名单必须集中在一处，这是安全设计不是欠账）、`types.ts`（DTO 唯一真源，铁律不变）。这些已经是「加功能只加文件」的形状，重排它们只有改动量没有收益。

## 1. 配置（config.json）

### 1.1 字段注册表 —— `src/shared/config-schema.ts`

```ts
interface ConfigField<K extends keyof AppConfig> {
  /** 读盘：把 config.json 里这个键的原始值（可能缺失/被手改坏）搬成合法值。幂等。 */
  read(raw: unknown, file: Record<string, unknown>): AppConfig[K]
  /** 出主进程：交给渲染进程的形状（第二道保险 + 整树新造）。 */
  expose(value: AppConfig[K]): PublicAppConfig[K]
  /** 保存：config:save 载荷里这个键的入参并进现有值。缺省 = 听现有的；类型错 = 抛。 */
  merge(incoming: unknown, current: AppConfig[K]): AppConfig[K]
}

export const CONFIG_FIELDS: { [K in ConfigFieldKey]: ConfigField<K> } = { … }
```

- `ConfigFieldKey = Exclude<keyof AppConfig, 'version' | 'envCache'>`。`version`（schema 版本）与 `envCache`（主进程写穿的缓存）**不听渲染层**，由三个入口函数直接处理，不进注册表。
- 映射类型保证：**往 `AppConfig` 加字段而不写注册表条目 = 编译不过**。
- `read` 的第二个参数是整份原始文件，只给需要看旧键的字段用（如 `nativeIdePaths` 要读旧的 `nativeIdePath`）。
- 三个入口函数保持原位、原签名（既有调用点与单测一行不改），实现变成遍历注册表：
  - `migrateConfig(raw)` —— `src/shared/config-migrate.ts`
  - `toPublicConfig(cfg)` / `mergeConfigPayload(current, payload)` —— `src/main/store/config-merge.ts`

### 1.2 版本迁移步骤表 —— `CONFIG_MIGRATIONS`（同在 `config-migrate.ts`）

```ts
/** 键 = 起始版本 n；函数把 vn 的原始文件**就地**改成 v(n+1) 的形状。 */
export const CONFIG_MIGRATIONS: Record<number, (file: Record<string, unknown>) => void> = {
  20: (file) => { delete file.pet; delete file.wallpaper; delete file.splash }
}
```

`migrateConfig` 先按 `file.version` 依次跑步骤表到当前版本，再过注册表的 `read`。

- **加字段**：只需注册表条目（`read` 对缺失值给默认）+ bump 版本 + 在 `types.ts` 版本表记一行。
- **删字段 / 改名 / 拆分 / 合并**（结构性变更）：再加一条步骤。
- v1 ~ v20 的历史变更全是「加字段」或已由字段的 `read` 幂等处理（含 v8→v9 的 `nativeIdePath` 拆分），不回填步骤表。
- 版本比当前还新（装回旧版）：不跑步骤，照常过 `read`（认识的留、不认识的丢），既有取舍不变。

## 2. 主进程：组合根 + 功能模块

```
src/main/
  index.ts          薄入口（定 userData 路径）—— 不动
  app.ts            组合根：启动前置检查 → 单实例锁 → 建 context → 注册全部 feature → 建窗口 → 生命周期
  context.ts        MainContext：≥2 个功能共用的服务（stores、配置读写口、档案读口、设备身份、云上行、主窗口）
  features/
    index.ts        FEATURES: MainFeature[] —— 功能清单，顺序即注册顺序（也是 dispose 顺序）
    <name>.ts       一个功能一个文件：该功能的全部 handle(IPC.…) + 只有它自己用的助手
                    现有：html-preview（协议 + iframe 请求拦截，两个 feature）、cet6、profile（含签到）、remote（手机连接，docs/29）、
                    wrongbook、favorites、memo、practice、config（含环境检测）、ai-questions、
                    study、ai-chat（会话 + 对话）、challenge、runner（含本地 IDE / 导出 Markdown）、
                    cloud（挑战结算入队 + 启动会话恢复，须在最后）
  （cloud/ runner/ env/ ai/ study/ store/ 等子系统目录保持原样，被 feature 调用）
```

```ts
export interface MainFeature {
  name: string
  /** app ready 之后、建窗口之前调用一次：注册 IPC handler、装协议。 */
  register(ctx: MainContext): void
  /** before-quit 时调用：收子进程、停定时器。 */
  dispose?(): void
}
```

规矩：

1. **IPC handler 一律经 `handle(IPC.x, fn)`（`src/main/ipc.ts`）注册，且只允许出现在 `features/` 下**。`handle` 内部调 `ipcMain.handle` 并把 `fn` 记进一张表，手机连接（docs/29）的远程调用从表里取同一个 handler；`features/` 之外直接写 `ipcMain.handle` 或 `handle(IPC.…)` 一律不允许。
2. 助手函数只被一个功能用 → 放进那个 feature 文件；被两个及以上用 → 放 `context.ts`。feature 之间**不互相 import**。
3. `app.ts` 里 `app.whenReady()` 之前的时序（调试端口、scheme 特权声明、数据目录可写检查、AppUserModelId、单实例锁）是硬约束，位置不许动。
4. `context.ts` 与各 feature 文件**模块顶层不许有副作用**（只放类型 / 函数 / 纯常量）：ES import 会被提升，顶层构造的东西会跑在 `app.ts` 的数据目录可写检查与 scheme 特权声明之前。构造全部发生在 `createMainContext()` / `register()` 里。账本、设备身份、token store 这类**急切构造**（读盘）的服务放在 context 里，由 app.ts 在原位置调用。
5. 依赖 `__dirname` 的路径（preload、渲染层 html、`study-math.js`）一律在 `app.ts` 算好，经 `createMainContext({ studyMathPath })` 传入 —— 主进程有三个 rollup 入口，功能代码可能落进别的输出目录的共享 chunk。
6. `dispose()` 没有参数：需要 ctx 里服务的 feature 在 `register` 时把句柄存进模块级变量。
7. 自定义协议的特权声明（`protocol.registerSchemesAsPrivileged`）**全进程只能调一次**，集中在 `app.ts`；功能自己的协议 handler 在 `register` 里装。

## 3. IPC 契约闸门 —— `src/main/__tests__/ipc-contract.test.ts`

静态扫描源码，断言：

- `window.miai` 用到的每个通道（`src/shared/miai-api.ts` 里 `t.invoke(IPC.x` / `t.on(IPC.x`），在 `src/main/features/` 下**恰好有一处** `handle(IPC.x`；preload 本身只是传输层，不点名任何通道；
- 没有重复注册（Electron 对重复 handle 是运行时抛错）；
- `features/` 之外没有 `ipcMain.handle`，也没有 `handle(IPC.…)`（登记口 `main/ipc.ts` 自己除外）。

另有 `src/shared/__tests__/remote-channels.test.ts`：每个 `IPC` key 必须恰好出现在手机白名单与拒绝名单之一。**新增通道在这里会红，必须决定手机能不能用**（docs/29 §2）。

## 4. 加一个新功能的清单

| 步骤 | 位置 |
|---|---|
| 1. DTO 类型 | `src/shared/types.ts` |
| 2. 通道名 | `src/shared/ipc-channels.ts` |
| 3. 主进程 | 新建 `src/main/features/<名>.ts`，在 `features/index.ts` 的 `FEATURES` 加一行 |
| 4. 白名单 | `src/shared/miai-api.ts` 的 `createMiaiApi` 追加方法（preload 与手机端共用；`window.miai` 类型自动跟着变）；`src/shared/remote-channels.ts` 决定手机能不能调 |
| 5. 渲染层 | `stores/<名>.ts` + `views/<名>View.vue` + `router/index.ts` 一行 + 侧栏入口 |
| 6. 需要设置项 | `types.ts` 的 `AppConfig` 加字段 → `config-schema.ts` 加条目 → bump `CURRENT_CONFIG_VERSION` + 版本表记一行（结构性变更再加迁移步骤） |
| 7. 需要自己的数据文件 | `src/main/store/stores.ts` 加一个 store（跟人走进盒，设备级不进盒），带 `version` + 读口归一化 |
| 8. 闸门 | `npm run typecheck && npm test`（含 IPC 契约闸门） |

**删一个功能**是同一张表倒着走；动了 `AppConfig` 就必须有迁移步骤（铁律 6）。
