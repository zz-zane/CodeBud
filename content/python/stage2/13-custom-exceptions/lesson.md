## 学习目标

本课学习异常进阶与自定义异常。重点包括异常体系、raise、自定义异常类、处理原则。请结合示例观察程序状态、执行顺序和结果，并通过练习检查理解。

## 毛病也有家谱：大家都姓 `Exception`

```python
print(issubclass(ValueError, Exception))
print(issubclass(ZeroDivisionError, Exception))
```

```text
True
True
```

我们碰到过的毛病长得五花八门：

| 纸条上写的名字 | 什么时候会甩出来 |
|---|---|
| `ValueError` | 给的东西**样子不对**，比如让我们把「字」变成数字 |
| `ZeroDivisionError` | 让我们除以 0 |
| `KeyError` | 按一个**不存在的名字**去抽屉里找东西 |
| `FileNotFoundError` | 去开一个**不存在的档案** |
| `TypeError` | 拿数字去和一段字相加这种「脾气不合」的活 |

看着各是各的，其实它们**全是从 `Exception` 这张父类底下一路创建后的**。调用一次 `issubclass(某个毛病, Exception)`，就是问一句「它是不是 `Exception` 的后代」，返回 `True` 就是「是」。

这件事有个很实在的用处：`except Exception:` 能把**所有这些后代**一网打尽 —— 因为接住的规矩是「**这毛病是它、或者是它的后代，都算接住**」。

## 一条条比：`except` 的顺序

```python
try:
    print(int("字"))
except ValueError:
    print("这不是数字")
except Exception:
    print("别的毛病")
```

```text
这不是数字
```

写了好几个 `except` 的时候，Python **从上往下一条条比**，**先对上的那条先接住**，后面的连看都不看。

所以顺序很要紧：`ValueError` 写在前面，它就接到了 `int("字")` 甩出来的纸条；要是把笼统的 `except Exception` 写在最前面，它会把**所有**后代都抢走，后面那条 `except ValueError` 一辈子轮不到。

**规矩就一句：具体的写前面，笼统的写最后。**

## 主动翻脸：`raise`

到目前为止，都是我们的代码**被动**挨纸条。其实我们也可以主动甩：

```python
def 分数据(份数):
    if 份数 <= 0:
        raise ValueError("份数得是正数")
    return "每份 1 条"

try:
    分数据(0)
except ValueError as e:
    print("抓到啦：", e)
```

```text
抓到啦： 份数得是正数
```

- **`raise 毛病的名字("纸条上写的话")`** —— 主动把纸条甩出去，后面那行 `return` 就再也轮不到了。上面的 `raise` 摆在一道 `if` 后面：传入的份数不合法，我们干脆**当场翻脸，而不是硬着头皮往下算**。这样出问题的地方离原因最近，抓起来最容易。
- `except ValueError as e:` 里的 **`as e`** 是把接到的**那张纸条本身**取个名字（这里叫 `e`），好拿在手里看。直接 `print(e)` 印出来的就是纸条上写的那句话。

## 想知道纸条上写的名字

`e` 是纸条本身，想拿到**上面写的那串名字**（`ValueError` 这种），用 `type(e).__name__`：

```python
try:
    print(10 / 0)
except ValueError:
    print("数值不对")
except Exception as e:
    print("别的毛病：", type(e).__name__)
```

```text
别的毛病： ZeroDivisionError
```

`10 / 0` 甩出来的是「除以 0」那张纸条，第一个 `except ValueError` 一看**不是自家后代**，放它过去；第二个 `except Exception` 把它接住，`type(e).__name__` 就取出纸条上那串名字 `ZeroDivisionError`。

## 接不住会怎样

```python
def 分数据(份数):
    if 份数 <= 0:
        raise ValueError("份数得是正数")
    return "每份 1 条"

print(分数据(3))
print(分数据(0))
```

解释器当场把纸条甩到我们脸上，程序**断了气**。我们把开头一行和最后一行抄下来：

```text
每份 1 条
Traceback (most recent call last):
ValueError: 份数得是正数
```

盯住输出的第一行：`每份 1 条` 印出来了，说明**前面那一句正常跑完了**；可第二句一翻脸，程序就在那儿断了气，后面的行**一行都没跑**。这就是为什么该接的地方要接住：**断气的位置和出毛病的位置常常隔着十万八千里**，越早接住越好查。

## 自己定义一个类：我们专属的毛病

前面用的全是现成的名字。要是有我们这摊活**特有的**毛病，比如「数据不够」，现成的名字都说不清，那就自己定义一个类：

```python
class 数据不够(Exception):
    pass

try:
    raise 数据不够("元素空了")
except 数据不够 as e:
    print("自己画的毛病：", e)
```

```text
自己画的毛病： 元素空了
```

- 画法就一行：**`class 名字(Exception):`**，底下写一句 `pass`（先占个位，意思是「类定义就这样，别的先不加」）。
- 括号里的 `Exception` 是关键：它是告诉我们「**这张新类定义是从父类底下创建后的**」，所以接住的规矩照样认它 —— `except 数据不够:` 接得住，`except Exception:` 也接得住。
- 有了自己的类定义，接住的时候就能**只接自己那种毛病**，不用把别的毛病一起兜进来。

## 处理原则：能接才接，接住要说清怎么办

画了类定义不等于到处乱接。我们给自己定了四条规矩：

1. **能处理才接。** 接住了要有办法往下走（比如给个默认值、重问一次、写进日志）。没办法处理就别接 —— 让它断气，比装作没事强。
2. **接住的地方要说清怎么办。** 空的 `except: pass` 是最危险的一种写法：毛病被吞掉了，程序**带着毛病继续往下跑**，等到后面炸出更大的窟窿，我们连原始线索都找不着了。
3. **具体的写前面，笼统的写最后**（上面那条规矩，再说一遍不嫌多）。
4. **别拿翻脸当日常的交通灯。** 能事先用 `if` 问一句就问一句；翻脸是留给**我们料不到、或者懒得事先检查**的场合的。

::: tip 提示
- **`try:` / `except 名字:`** —— 先试一手；甩出来的纸条是它、或者是它的后代，就接住。
- **`raise 名字("话")`** —— 主动甩纸条；后面那些行就都轮不到了。
- **`except 名字 as e:`** —— 把纸条本身取个名字拿在手里；`print(e)` 看内容，`type(e).__name__` 看名字。
- **自己定义类**：`class 我们的毛病(Exception): pass`。必须套着 `Exception` 才有「后代」这层身份。
- **四个 `except` 按「具体→笼统」排**，先对上的先接住。
- 接不住就断气，**断气之后的行一行都不跑**。
:::

::: warn 注意
- **`except Exception: pass`** —— 把毛病吞进状态。程序看着还在跑，其实已经带着毛病了，过一会儿炸在别处，线索全丢。至少要 `print` 一句。
- **`except Exception` 写在最前面** —— 它会把后面所有具体的 `except` 全抢走，那几条一辈子轮不到。
- **自己画的类定义忘了套 `Exception`** —— 写成 `class 数据不够:` 也能过（解释器不拦你），可它就不是后代了。后果比「接不住」还绕，我们量给你看：想甩 `raise 数据不够("没了")` 的时候，甩出去的**根本不是你的类定义**，是解释器自己的一张 `TypeError: 数据不够() takes no arguments`（意思是：这张类定义压根不接**参数**）；写成 `raise 数据不够`（不带括号）又换一句 `TypeError: exceptions must derive from BaseException`。最气人的是，这两句 `TypeError` **反倒被 `except Exception:` 接住了** —— 屏幕上压根不出现「数据不够」四个字，只出现一句跟你的毛病八竿子打不着的 TypeError，我们盯着它看半天也想不到是忘套了那张父类。一句话：**套上 `Exception` 是给它上户口**，不上户口，连甩都甩不出去。
- **接住之后当没发生过** —— 接住了就得**处理**：要么给个合理的替代值，要么老老实实告诉用户「这一步没成」。
:::

## 一句话对照表

| 写下的这一句 | 它干了什么 |
|---|---|
| `except ValueError:` | 只接这种毛病（以及它的后代） |
| `except Exception:` | 把所有的后代一网打尽（要写在最后） |
| `raise ValueError("话")` | 主动翻脸，甩出一张纸条 |
| `except 名字 as e:` | 接住，并把纸条本身交到 `e` 手里 |
| `type(e).__name__` | 取出纸条上写的那串名字 |
| `class 数据不够(Exception): pass` | 画一张自己的毛病类定义 |

## 小任务

我们写了一个「按名字查号码」的函数，遇到两种毛病：

```python
通讯录 = {"咪爱": "123-456"}

def 查号码(名字):
    if 名字 not in 通讯录:
        raise KeyError(f"没有这位朋友：{名字}")
    return 通讯录[名字]

try:
    print(查号码("咪爱"))
    print(查号码("小狸"))
except KeyError as e:
    print("没查到：", e)
```

```text
123-456
没查到： '没有这位朋友：小狸'
```

（顺带认一个小脾气：这行纸条印出来**自带一对引号**。毛病名字里带 `Key` 的那一族都有这个习惯，我们不用管为什么，认得它就行。）

**试着改一改**：

1. 把 `raise KeyError(...)` 换成 `return "查不到"`，再跑一遍 —— 哪种写法更好？想想「查不到」到底算不算毛病。
2. 自己画一张 `class 没有这位朋友(Exception): pass`，把上面那句 `raise` 换成甩自己的类定义，`except` 也跟着换。
3. 在 `except` 里加一句 `print(type(e).__name__)`，看看纸条上写的名字长什么样。
