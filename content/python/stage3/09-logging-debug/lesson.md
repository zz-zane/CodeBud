## 学习目标

本课学习日志与调试技巧。重点包括logging、断点、pdb 初步、排查思路。请结合示例观察程序状态、执行顺序和结果，并通过练习检查理解。

## 最土的办法：每走一步调用输出方法

新手最先学会的招是往代码里塞 `print`。我们也这么干过：

```python
def 分数据(总数, 对象数):
    print("总数", 总数, "对象数", 对象数)
    每个 = 总数 // 对象数
    return 每个

print(分数据(10, 3))
```

```text
总数 10 对象数 3
3
```

我们在函数中间塞了一句 `print`，把当时手里的两个数输出（`print` 的老规矩：逗号隔开的东西之间会插一个空格）。跑一遍就看见了：进去的时候是「总数 10 对象数 3」，出来的是 `3`。**中间那一步不再是一团黑**。

这招确实管用，可它有四个毛病：

1. **输出和正文混在一条渠里。** 程序真正要给用户看的那句，和我们自己嘟囔的那句，长得一模一样，谁是谁分不清。
2. **用完得想起来删。** 忘删一句，你的程序就永远对着用户多吐一行莫名其妙的字。
3. **没有轻重之分。** 一天里调用了二十句，哪句是小事、哪句是着火了，得从头一句句读。
4. **只能看，不能留。** 今天跑出来的那几行，明天再跑一遍就没了，出了事翻不出旧账。

## 值班小本子：日志

我们换个法子：在灶台边放一个**值班小本子**。每做完一步就往上写一行：做了什么、顺不顺、有多要紧。这本子有正式名字，叫**日志**。

Python 里管这本子的家伙什叫 `logging`，是自带的一盒工具，`import` 一下就能用。

```python
import logging

logging.warning("数据库存只剩 3 条了")
print("处理完成")
```

```text
处理完成
```

咦，等一下 —— **那行警告呢？** 明明写了，怎么正文里一个字都没有？

因为日志默认**不住在正文那条渠里**。程序往外说话其实有**两条渠**：一条是**正文**（`print` 走的那条），一条是**侧渠**（旁注、警告走的那条）。`logging` 默认往侧渠倒，`print` 往正文倒，两条渠互不打扰。

这正是日志比 `print` 强的地方：**你可以让本子一直开着**，它不会混进程序真正的输出里。要看的时候，去侧渠里翻本子就行。

反过来说也有一条要紧的后果：**只接正文那条渠的地方**（比如你把输出存成文件、或者别的程序来读你这边的输出），**日志就一个字都看不见**。想让日志在那里现身，得亲自动手把本子挪过去 —— 下一节就干这件事。

## 把本子挪到正文：`basicConfig`

```python
import logging
import sys

logging.basicConfig(stream=sys.stdout)

logging.warning("数据快没了")
```

```text
WARNING:root:数据快没了
```

`logging.basicConfig(...)` 是「**给值班小本子定规矩**」的函数：调用一次，往后每一条日志都照这个规矩写。它的规矩是一次性的，所以摆在最前面。

- **`stream=sys.stdout`** —— 把本子上的字往**正文那条渠**倒。不写它，默认还是倒进侧渠。`sys.stdout` 就是「正文那条渠」在代码里的名字（`sys` 是 Python 自带的另一盒系统工具）。
- 印出来的那一行分三段：`WARNING`、`root`、`数据快没了` —— 也就是**级别、署名、消息**。中间那个 `root` 是小本子的**署名**，默认就叫这个名字。
- **默认版式里没有时间。** 想记时间得自己把版式写出来，我们这里先不展开。

### 自己定版式：`format`

```python
import logging
import sys

logging.basicConfig(stream=sys.stdout, format="%(levelname)s:%(message)s")

logging.warning("数据快没了")
logging.error("任务失败")
```

```text
WARNING:数据快没了
ERROR:任务失败
```

- **`format=`** 是「这一行长什么样」的类定义：`%(levelname)s` 表示「把级别的名字填这儿」，`%(message)s` 表示「把消息填这儿」，中间那个冒号是我们自己写死的分隔符。
- 这一下把署名丢掉了 —— 本子上只剩级别和消息，干净多啦。

## 级别：一句话说清有多要紧

我们给本子上的每一条都盖个戳，一共五档，从轻到重：

| 级别名 | 什么时候盖 | 我们的说法 |
|---|---|---|
| `DEBUG` | 只有我们自己关心的细节 | 对象毛掉了几根 |
| `INFO` | 一切正常，通报一次 | 鱼汤开始咕嘟了 |
| `WARNING` | 有点不对劲，但还走得下去 | 数据快没了 |
| `ERROR` | 这一步没干成 | 任务失败 |
| `CRITICAL` | 整个灶台都完了 | 厨房冒烟了 |

盖戳的函数，名字就是级别名的小写：`logging.debug(...)`、`logging.info(...)`、`logging.warning(...)`、`logging.error(...)`、`logging.critical(...)`。

**大小写是两回事，这里要先说死：** 函数的名字是**小写**的（`logging.warning`），而写在关卡那里的那块名称是**全大写**的（`logging.WARNING`）。大写那块名称上写的是一个**编号**，不是一个方法。你要是把它当函数调用，程序当场就断气：

```python
import logging

logging.DEBUG("这句写错了大小写")
```

```text
Traceback (most recent call last):
    logging.DEBUG("这句写错了大小写")
TypeError: 'int' object is not callable
```

（我们照旧把中间那行「文件在哪」的路径省掉了，那是每跑一次都不一样的一串字。）

**级别不只是给你看的标记，它还是一道筛子。** `basicConfig(level=...)` 就是「关卡设在哪儿」：比这条线**轻**的一律不写进本子。

```python
import logging
import sys

logging.basicConfig(stream=sys.stdout, level=logging.INFO, format="%(levelname)s:%(message)s")

logging.debug("这句太啰嗦")
logging.info("开始煮鱼汤")
logging.warning("数据快没了")
```

```text
INFO:开始煮鱼汤
WARNING:数据快没了
```

三句日志只印出来两句：`DEBUG` 那句比关卡的 `INFO` **轻**，被挡在门外了。

而**不写 `level=` 的时候，关卡默认设在 `WARNING`** —— 所以 `debug` 和 `info` 平时一个字都不留，只有 `warning` 和更重的才写得进去。这条默认设定很省事：正常日子里本子安安静静，一旦它开始说话，多半是真有事。

::: tip 提示
今天的前半课，三句话记住：

- **`print` 是正文的作者**，日志默认走侧渠；两条渠互不打扰。
- **`basicConfig(stream=sys.stdout)`** 才把日志挪到正文；**`level=`** 是关卡的线，比线轻的都不写，默认的线在 `WARNING`。
- **`format=`** 定版式：`%(levelname)s` 是级别名，`%(message)s` 是消息。
:::

## 让程序停下来：暂停小旗

上面那些办法都是「让程序自己说话」。可有时候你想知道的是：「跑到第 5 行的时候，那个元素里到底保存什么？」

这时候有个更直接的办法：**在那一行插一面小旗**。程序跑到小旗那儿就**停住**，变量悬在半空 —— 你这时可以随便翻看，看够了再让它继续走。书上管这面小旗叫**断点**。

我们得先交代一件事：**「停下来看」是交互式的**。程序一停，它就**等你敲键盘**；你不敲，它就一直杵在那儿。所以今天这一课里没有「跑得起来的小旗示例」—— 只要把小旗摆进示例，那段示例就会停在那里等，永远跑不完。今天只讲思路：它是什么、什么时候该用它。

## `pdb`：Python 自带的调试小助手

那面小旗输出的，是一个住在 Python 家里的**调试小助手**，书上叫它 `pdb`。

请它出来的办法有两种（先看个眼熟，别急着背）：

- 在代码里想停下的那一行写一句 `breakpoint()`，程序跑到那儿自动停下；
- 或者在终端里写 `python -m pdb 你的脚本.py`，请它从第一句就开始陪着。

它一登场，终端里会出现一个 `(Pdb)` 的小提示符，等着你敲命令。

### `(Pdb)` 里最常用的五条命令

```text
n        走到下一句（不钻进函数内部）
s        钻进这一句里的函数，看它里面怎么走
p 名字    把某个名字此刻的值印出来（p 就是 print 的缩写）
c        别停了，一路跑完
q        不玩了，收工退出
```

最省力的用法是这样：先 `n` 一句句走，走到可疑的地方用 `s` 钻进去，看见不认识的名字就 `p` 一下，确认没问题就 `c` 让它一口气跑完。

::: warn 注意
两个特别容易踩的坑：

- **别在正式交付的程序里留下 `breakpoint()`。** 它会让程序停下来等人 —— 你不在旁边敲键盘，它就永远卡在那一行，看起来像「程序死了」。
- **日志默认不进正文那条渠。** 你要是拿「正文里有没有这行字」当判据，会一直找不到它 —— 先 `stream=sys.stdout` 挪过去，或者记着去侧渠里翻。
:::

## 三条调试思路

家伙什讲完了，最后是我们踩了无数坑攒下的三条思路。

### 一、先读**最后一行**

报错信息不是一团乱麻，它是有顺序的。把下面这段故意写坏的代码跑一遍：

```python
def 煮汤(鱼的条数):
    倒进锅里(鱼的条数)

def 倒进锅里(条数):
    print(条数 / 0)

煮汤(3)
```

```text
Traceback (most recent call last):
    煮汤(3)
    倒进锅里(鱼的条数)
    print(条数 / 0)
ZeroDivisionError: division by zero
```

（中间那几行「当时跑到哪儿了」的现场记录我们抄了下来；每一行开头还夹着一串「文件在哪」的路径，那是每跑一次都不一样的一串字，我们就省掉啦。）

怎么读这张纸条：

- **最后一行**告诉你**出了什么事**：`ZeroDivisionError: division by zero` —— 「除以零」这件做不到的事被干了。
- **上面那几行**告诉你**出事时走到哪儿了**：一路从 `煮汤(3)` 走到 `倒进锅里(鱼的条数)`，最后停在 `print(条数 / 0)` 那一句上。**离最后一行最近的那句，就是案发现场。**

所以调试的第一个动作永远是：**从最下面往上读**。新手最容易犯的错是从上往下读，被开头那几行吓住，其实重点在最底下那句。

### 二、把范围砍一半

我们不知道十步里哪一步坏，就先查第 5 步：没问题 —— 那就说明毛病在后五步；再看第 8 步……每问一次，可疑的范围就少一半。这比从第一行开始一句句干瞪眼快得多。

### 三、一次只改一处

猜一个原因，改**一处**，立刻跑一遍。别一口气改五处 —— 跑通了你不知道是哪个改对了，跑不通你更不知道该退哪一处。**先猜再验，一步一步来**，这是调试最省时间的习惯。

## 小任务

我们写了一段「带小本子的分数据」，你照着敲一遍跑跑看：

```python
import logging
import sys

logging.basicConfig(stream=sys.stdout, level=logging.DEBUG, format="%(levelname)s:%(message)s")

def 分数据(总数, 对象数):
    logging.debug(f"总数={总数} 对象数={对象数}")
    每个 = 总数 // 对象数
    logging.info(f"每个分到 {每个} 条")
    return 每个

logging.warning(f"分数据的结果是 {分数据(10, 3)}")
```

```text
DEBUG:总数=10 对象数=3
INFO:每个分到 3 条
WARNING:分数据的结果是 3
```

**试着改一改**：

1. 把 `level=logging.DEBUG` 改成 `level=logging.INFO`，再跑一遍 —— 哪一行消失了？为什么是它？
2. 把 `stream=sys.stdout` 整段删掉，再跑一遍 —— 正文里还剩什么？（提示：先猜一猜再跑。）
3. 把最后那句 `logging.warning(...)` 换成 `logging.error(...)`，印出来的第一段会变成什么？
